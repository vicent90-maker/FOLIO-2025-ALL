# 访客审批门禁系统 · 想法与方案草案（Folio 2025）
> 关联文档：`docs/划地盘.md`（领地范围）、`docs/项目记忆库.md`
> 关联代码：`sources/Game/World/TerritoryFence.js`（石围栏 + 大门）、`sources/Game/World/PandoraFence.js`（竹子围栏）、`sources/Game/Accounts.js`（本地版账号系统 + 登录注册界面）、`sources/Game/TerritoryRegistry.js`（地块登记表）、`sources/Game/Territory.js`（当前领地数据）
> 本文用途：**讨论前的输入材料**——用于对齐"服务器能力"与"分工边界"，不是最终技术方案

---

## 1. 一句话目标

给每块玩家领地装上「门」。领地主人可自由进出；其他访客开车到门口后按**右键**发起访问申请，经**主人审批**（接受 / 拒绝）后，门才打开。

---

## 2. 原始想法（10 条）

1. 一进去就要登录，登录之后就是你。
2. 首先你要注册你的身份信息。
3. 代码会自动锁定你是哪个地盘的主人。
4. 我到时候再给我的地盘开个门。
5. 如果你不是地盘的主人，就不能进去，你只能靠近那个门。
6. 当你走近一点到门的位置时，可以按下右键。
7. 按下右键就是你想进入这个地盘。
8. 你要经过主人的审批，这个时候联机就开始了。
9. 这个时候，地盘主人那边的弹窗上就显示"某某某要来访问你的地盘"。
10. 接受还是拒绝？如果选择接受，大门就会打开；如果选择拒绝，门外的人就不能进。

---

## 3. 现状对照：每条靠什么实现

> 现状背景：当前项目是**纯静态的单机网页站**（Vite 构建，无服务端依赖）。

| # | 想法 | 实现层 | 现状 |
| --- | --- | --- | --- |
| 1 | 进去要登录 | 账号系统 | ❌ 需后端 |
| 2 | 注册身份信息 | 账号系统 | ❌ 需后端 |
| 3 | 自动锁定你是哪块地主 | 服务端「账号 → 领地」映射 | ❌ 需后端（目前领地写死在 `TerritoryRegistry.js`） |
| 4 | 给自己的地盘开门 | 门（纯前端物理） | ⚠️ 围栏已有、门没有，**可做** |
| 5 | 非主人不能进，只能靠近门 | 门常闭 + 碰撞体 | ⚠️ **可做** |
| 6 | 走近门按右键 | `inputs` 输入系统 | ✅ 项目已有现成系统 |
| 7 | 右键 = 申请进入 | 交互逻辑 + 发送请求 | ⚠️ 前端可做，"发送"需后端 |
| 8 | 主人审批，联机开始 | 实时通信（WebSocket） | ❌ 需后端 |
| 9 | 主人端弹窗提示 | `modals` / `notifications` | ✅ 项目已有现成系统 |
| 10 | 接受/拒绝 → 开门/不开 | 前端 UI + **服务端裁决** | ⚠️ UI 可做，裁决需后端 |

**结论：**
- **前端部分（4~7、9、10）** 依赖项目已有的 `inputs`、`modals`、`notifications`、`objects.setEnabled()` 四套系统即可完成，工作量可控。
- **后端部分（1、2、3、8）** 是必须新增的基础设施，是本方案能否成立的分水岭。

## 4. 系统构成

### 4.1 三块拼图

| 部分 | 职责 | 归属 |
| --- | --- | --- |
| **身份** | 判断"开车这人是谁、是不是某块地的主人" | 后端（账号 + 归属表） |
| **门** | 一个**独立物理刚体**，可整体开关 | 前端（`TerritoryFence` 扩展） |
| **审批** | 访客发起 → 主人接受/拒绝 → 门开/不开 | 前端 UI + 后端裁决 |

> ⚠️ **共键技术点**：门体必须是**独立的物理刚体**，不能与相邻栏板共用。因为开关用的是 Rapier 的 `RigidBody.setEnabled()`，它会关闭**整个刚体**；若共用，旁边的栏板会一起失效，围栏上会出现缺口。

### 4.2 完整流程

```text
访客                          服务端                        主人
 │                              │                            │
 │ 1. 登录（获得身份）            │                            │
 ├─────────────────────────────►│ 2. 校验账号                 │
 │                              │ 3. 返回"你是访客 XXX"          │
 │◄─────────────────────────────┤                            │
 │                              │                            │
 │ 4. 开车到门口，走近            │                            │
 │ 5. 按下右键 → 发起访问申请      │                            │
 ├─────────────────────────────►│ 6. 转发来访请求              │
 │                              ├───────────────────────────►│
 │                              │   7. 弹窗："XXX 想来访问"      │
 │                              │                            │
 │                              │◄───────────────────────────┤
 │                              │   8. 主人点【接受】/【拒绝】   │
 │                              │ 9. 记录"XXX 已获准通行"        │
 │◄─────────────────────────────┤                            │
 │ 10. 门开（服务端下发许可）      │                            │
 │ 11. 开车进入                   │                            │
```

> 📌 **第 9、10 步必须由服务端记录与下发。** 若"我有没有被批准"由前端自行判断，访客只需修改本地代码即可骗过大门——门禁就形同虚设。

## 5. 需要服务器提供的能力

| 能力 | 用途 | 对应想法 |
| --- | --- | --- |
| 账号系统 | 注册 / 登录 / 记住"你是谁" | 1、2 |
| 数据存储 | 「账号 → 领地」归属映射、通行记录 | 3 |
| 实时消息 | 访问申请与审批结果的即时推送 | 8、9 |
| 权限裁决 | 服务端判定"此访客此刻可否通过" | 10 |
| 在线状态 | 判断主人是否在场（决定能否审批） | 8 |

## 6. 服务器能力确认清单（讨论时逐条确认）

### 6.1 先确认服务器的档次

| 档次 | 服务器形态 | 本方案可达程度 |
| --- | --- | --- |
| **A** | 能跑常驻进程（Node / Python）、能开端口、能装数据库 | ✅ 10 条全部可做 |
| **B** | 只有 Serverless / 云函数（被动触发、有执行时限） | ⚠️ 账号可做，**实时推送勉强** |
| **C** | 只能托管静态文件 | ❌ 等于没有 |
| **D** | 现成第三方平台 | ⚠️ 取决于其开放能力 |

### 6.2 五个必问问题

1. 那台服务器现在在跑什么？能不能跑**常驻进程**和**数据库**？
2. 谁能部署、谁能修改？改动是否需要通知他人？
3. 这套是**老师提供**的还是**同学自建**的？（决定报备流程、出资与维护责任）
4. 支持**多少人同时在线**？（"主人在线才能审批"直接受此限制）
5. 有没有**域名和 HTTPS**？（否则账号传输不安全，且浏览器多项能力受限）

### 6.3 回声测试（建议先做，只花 1 小时）

> **开两个浏览器：A 点击一个按钮，B 端立刻弹出"有人来了"。**

一次验证三件事：服务器能否**实时通信**、能否**跨网络**、队员是否**愿意配合**。
跑通 → 再谈完整方案；跑不通 → 方案需降级，可省下数天空想。

## 7. 关键设计决策（需共同拍板）

### 7.1 四个方向性决策

1. **领地归属表放哪**：服务端统一维护「谁拥有哪块地」，还是各人写在自己代码里？
   → 建议前者，否则无法实现"自动锁定主人"。
2. **门要不要统一实现**：全班共用一套 `TerritoryFence` + `gate` 参数，还是各写各的？
   → 建议统一，可省大量返工（石围栏与竹子围栏已是同类需求）。
3. **访客进去后能干什么**：只能走路参观？还是也能开车、能触碰物体？
   → 这决定权限模型要做多细。
4. **谁长期维护服务端**：必须有人认领，否则热度过后谁都进不去自家地盘。

### 7.2 八个细节设计点

| # | 待定问题 | 建议方案 |
| --- | --- | --- |
| 1 | 主人不在线怎么办 | 自动拒绝 + 提示"主人不在，稍后再试" |
| 2 | 批准一次 = 进一次？还是限时 | 发**限时通行证**（如 60 秒内有效） |
| 3 | 访客进去后门何时关 | 进入后自动关闭，防止他人跟随进入 |
| 4 | 多人同时申请 | 排队逐个弹窗，或合并为一条通知 |
| 5 | 访客进入后的权限边界 | 需明确（防破坏） |
| 6 | 主人自己进是否走审批 | 不走，直接放行 |
| 7 | 注册需要哪些信息 | 最简：昵称 + 口令，不要求实名 |
| 8 | 连不上服务器时 | **门默认关闭**（安全默认） |

## 8. 分期计划（建议）

| 阶段 | 内容 | 依赖后端 | 可否立即开始 |
| --- | --- | --- | --- |
| **P0** | 地盘开门 + 走近提示 + 右键"敲门" + **本地模拟审批**（自己弹给自己看） | 不需要 | ✅ 可立即开始 |
| **P1** | 注册登录 + 账号→领地映射 + 在线状态 | 需要 | 待能力确认 |
| **P2** | 申请/审批走实时通信，主人端弹窗实时出现 | 需要 | 待能力确认 |
| **P3** | 服务端裁决 + 限时通行证 + 防跟随 + 防滥用 | 需要 | 待能力确认 |

> **建议先做 P0**：可完全脱离后端，先验证交互手感与门的物理表现，同时保有一个"能演示"的版本。

## 9. 风险与前提

1. **客户端不可信**：开门许可必须由服务端裁定，否则可本地伪造。
2. **主人必须在线**：这是"人工审批"的天然限制，需明确离线策略（见 7.2-1）。
3. **部署形态会变**：现在是纯静态站；一旦引入后端，托管方式必须调整（静态托管平台无法承载常驻服务）。
4. **升级范围是全班**：登录流程、领地归属、服务端都属于共用部分，需与叶老师统一设计与分工，避免多人并行各改各的。
5. **门的实现需统一**：都存在同样的"主人进不去"问题，适合一并抽象为通用组件。

## 11. 进展记录（2026-10-18 补充）

### 11.1 需求补充

**注册后要能绑定地块**：注册完成时，让玩家从「可认领地块列表」里挑一块，绑定后就成为该地块的主人（想法第 3 条的具体化）。

### 11.2 P0 已实现（纯前端，无后端）

- 石围栏东边界拆成两段，留出 6m 门洞；门体是**独立刚体**，开门 = `setEnabled(false)` + 门扇绕门轴转 90°，关门反之
- 走近门口 8m 内出现底部提示；**右键**触发敲门
- 门开着后，玩家开离门口 15m 外等 2 秒自动关门（防止他人跟随进入，对应 7.2-3）
- 访客右键 → 弹出审批窗（Accept / Reject），P0 为本地模拟审批
- **出门不需要审批**：人在领地内侧右键直接开门（对应 7.2-6）

### 11.3 本地版账号系统（P1 的前身）

在没有服务器的前提下，先用浏览器 `localStorage` 做一个**本地版**账号系统，把「注册 → 绑定地块 → 登录 → 门禁判定」整条链路跑通：
- 注册 / 登录 / 绑定地块 / 登出，密码用 PBKDF2 加盐哈希后存储
- 门禁的"主人"判定从"人在领地内"的近似，换成"当前账号是否是这块地的主人"
- ⚠️ **明确的安全边界**：localStorage 可被任意修改，任何人打开开发者工具就能冒充主人。因此这套**只用于本地演示与交互验证**；真正上线时必须把这一层换成服务端接口（对应第 9 节风险 1）
